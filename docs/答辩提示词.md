## 三、高频问题预测与回答话术（按类别）

### A. 项目概述与动机类

**Q1｜你们这个系统到底是做什么的？（一句话）**

- 评分点：能不能 30 秒说清定位。
- 话术："一句话——**把工厂设备检修从'纸质工单 + 老师傅经验 + 线下签字'变成'数字化闭环 + AI 辅助 + 全程留痕'**。报修、高危作业审批、派工执行、完工质检、经验归档，全流程一个系统管到底。"
- 追问应对：若追问"给谁用"→"面向制造业工厂的设备维保部门，角色覆盖管理员、维保主管、检修技师、安全监护、一线操作工等 9 类岗位账号。"

**Q2｜为什么要做这个？行业痛点是什么？**

- 评分点：痛点是否真实、有数据。
- 话术："我们调研了真实检修现场，三个痛点：**一是流转慢**，纸质工单从报修到闭环要 3～5 天，中间全靠人催；**二是经验断代**，诊断靠老师傅，新人独立上手难；**三是安全失控**，高危作业票线下签字、纸质存档，'作业票开了但没按票干活'根本管不住。我们的系统用数字化闭环把这三件事管起来。"
- 追问应对："这个调研是真的吗？"→"我们做了需求走查和访谈提纲、三份岗位问卷（安全员/检修工/班组长），证据在 `docs/问卷-*.md` 和 `docs/走查访谈提纲.md`，可现场打开。"

**Q3｜市面上有 CMMS、EAM、MES 了，你们跟它们比差异在哪？**

- 评分点：不贬低对手，突出差异定位。
- 话术："市面系统强在资产台账和计划管理，但我们切入的是**国内中小工厂检修现场最痛、最缺监管的一段：高危作业安全管控 + AI 落地可靠性**。具体差异三点：①六类高危作业票双人会签 + LOTO 锁具物理状态联动，工业现场安全底线；②AI 不是玩具——降级不伪造、人工审核闸、知识溯源，敢在产线上用；③我们是一整套可一键部署的开源形态工程，中小工厂拿得起、跑得动。"
- 追问应对：被质疑"覆盖度不如大厂"→"我们不追求功能堆砌，产品定位就是'1 条高危作业闭环主线 + 高可靠 AI'，先做深再求广，扩展能力做成可插拔。"

**Q4｜哪些功能是你最自豪的？**

- 评分点：回答与创新点呼应。
- 话术："三件事：**①高危作业票 + LOTO 能量隔离的双人会签与锁具联动**——这是出了事故会出人命的功能，我们做得最重；**②AI 治理闭环**——AI 生成的东西必须先过人工审核闸才能入库，再用 RAG 引用，形成信任飞轮；**③攻击链回归测试**——把真实漏洞写成永久测试用例，安全基线默认拒绝。"

### B. 创新点类

**Q5｜创新点到底在哪？（必问，讲三条）**

- 评分点：创新是"工程创新"而非"模型自研"，不吹牛。
- 话术："我们讲三个工程创新：**①AI 治理闭环**——AI 产出 → 人工审核闸 → 知识沉淀 → RAG 再引用，解决 AI 在工业场景'敢不敢信'的问题；**②攻击链回归测试**——把真实安全漏洞（任意 JWT 拖源码）写成永久测试用例，安全基线默认拒绝；**③AI + 规则双轨可审计**——同一功能双实现、可降级、可对比，每次调用/降级/切换都有审计日志。"
- 追问应对：被质疑"这不都是常规工程做法？"→"对，我们刻意不做花架子。这些做法单独看都常见，但**组合成一个敢在工厂产线上用的完整闭环，并且每个环节都能现场验证、可审计**，这是我们的工程完整度。"

**Q6｜最难啃的骨头是什么？**

- 话术："两个：**一是安全合规流程的建模**——双人会签、二次安全密码核验、SHA-256 电子签名、LOTO 锁具状态联动，任何一步错了都影响真实安全；**二是 AI 的可靠性工程**——模型超时、没配 Key、返回乱码，怎么保证系统不崩、流程不中断、还绝不伪造结果。这两块我们分别用状态机互斥 + 降级契约来解决。"
- 追问应对："具体怎么保证不伪造？"→"三件事：失败返回 HTTP 200 + `degraded: true` 显式标记而不是假装成功；规则引擎兜底结果和 AI 结果严格区分；所有回答强制带 `knowledgeSources` 溯源，找不到依据就不答。"

### C. AI 相关（评委最爱打这个点）

**Q7｜AI 不就是调 API 吗？（高频打击题）**

- 评分点：区分"能力数量"和"工程深度"。
- 话术："调 API 只是能力数量。我们做的是**三层工程**：**容错层**——多模型路由、失败自动切换、每次调用/降级/切换全审计；**密钥安全层**——API Key 用 AES-256-GCM 加密存储，不落明文；**结果治理层**——人工审核闸 + 知识溯源，AI 产出的东西先过审再入库。能力分层我们自己很清楚：派单、报警是业务规则；诊断、方案是 RAG + 生成；视觉调用多模态模型；支撑层（鉴权、审计、降级、知识库）全部自研。"
- 追问应对："那你们的自研含量到底在哪？"→"在支撑层和治理层——AI 只是大脑，让大脑在工业环境里安全干活的那套系统是我们自己写的，这才是护城河。"

**Q8｜AI 出错了怎么办？工业场景敢用吗？**

- 评分点：给出"三道防线"，强调人永远是责任人。
- 话术："三道防线：**①降级不伪造**——AI 不可用时自动降级到确定性规则引擎，页面明确标注 degraded，绝不假装成功；**②人工审核闸**——AI 生成的检修方案、JSA 风险预审必须人工 approve 后才入库生效；**③溯源**——每个回答带知识来源，不可靠就不回答。AI 的定位永远是辅助决策，**人永远是最终责任人**。"
- 追问应对："规则引擎兜底质量够吗？"→"规则引擎覆盖的是高频、确定性的场景（气体检测阈值、防重复、派单推荐），AI 负责的是开放性问题，两者按场景分层，降级时用户看到的是可用但不完美的结果，而不是错误结果。"

**Q9｜没网、没 Key 演示会崩吗？**

- 话术："不会。所有 AI 接口无 Key 时自动降级为规则引擎结果，页面正常显示、工单照常流转。这一点我们有专项测试 `tests/ai-verification.test.ts` 验证降级契约，`tests/ai-features.test.ts` 验证离线模式全量可用。"
- 追问应对："演示时敢现场拔 Key 吗？"→"敢，这是我们准备的固定演示动作之一，拔掉 Key 后 AI 区域显示降级标记，业务流程不中断。"

**Q10｜AI 真实效果如何？有评测吗？**

- 评分点：用实测证据，不编准确率。
- 话术："有。我们做了**真实效果评测**：15 条故障诊断样本 + 4 张视觉质检图片，实测 100% 通过（2026-09-14，报告在 `docs/AI真实效果评测报告.md`，脚本 `scripts/ai-real-eval.ts` 可复现）；无 Key 降级模式 12 条固定样本 11/11 通过；PostgreSQL 生产模式核心回归 15/15。我们不报'准确率'这种虚数字，只报可复现的评测记录。"
- 追问应对："样本会不会太少？"→"会，我们承认样本规模有限，评测脚本已保留，后续会持续扩充样本库——这本身也是我们把'可复现评测'当工程做的体现。"

**Q11｜24 项 AI 能力是不是凑数？**

- 话术："不是。按 `/api/v1/ai/*` 路由去重统计，每项对应一个真实接口，注册代码可现场数。内部能力分三层：**业务规则层**（派单、报警、阈值检测、遥测统计）、**AI 生成层**（故障诊断、检修方案、报告）、**多模态层**（视觉质检、语音转写、数字人播报等），支撑层全部自研。"
- 追问应对：若被要求"说几个具体的"→"诊断、方案草拟、JSA 预审、知识问答、健康预测、视觉初筛、语音转写、数字人播报……每个在系统里都能点开。"

**Q12｜混合 RAG 为什么这么设计？（技术深问）**

- 话术："我们做了**向量语义检索（DashScope text-embedding-v3，1024 维）+ 关键词 BM25 的 RRF 融合**。选 RRF 而不是加权求和，是因为 RRF 对排名敏感而非分数敏感，避免了向量余弦分和关键词分**量纲不可比**的问题；k=60 是学术常用值（Cormack et al. 2009），在我们的知识库上实测召回最优。所有回答强制带 `knowledgeSources` 溯源，找不到依据就不答。"
- 追问应对："没装 pgvector 怎么办？"→"向量存储做了双模式：PG 装了 pgvector 用 HNSW 索引；没装就降级为 JSONB 数组 + 应用层余弦计算——14 篇文章 × 1024 维全表拉取约 56KB，计算 <5ms，当前规模完全可接受，千级文章再切索引。"
- 追问应对："向量维度怎么保证一致？"→"两层校验：embedding 服务返回前校验维度，不对就返回 null 走降级；写入前再契约校验，宁可报错也不写入错误维度污染余弦计算。"

**Q13｜AI 生成的检修方案，错了谁负责？（审核闸）**

- 话术："**审核闸兜底 + 人负责**。AI 生成的方案登记为 `pending`，只有审核人 approve 后才入库生效；审核用 `UPDATE ... WHERE status='pending' RETURNING id` 原子流转，两个人同时点也只能一个人成功，不会重复审核。审核人、时间、意见全落库，可追溯。"
- 追问应对："审核人会不会就是走个形式？"→"审核动作、意见、时间全部留痕，系统里可查；而且入库后的方案会被 RAG 再次引用，质量差的方案会污染检索结果，所以审核环节我们有意识地做重。"

### D. 技术与架构类

**Q14｜技术栈为什么这么选？**

- 话术："原则是**验证成本最低、最贴近真实工业软件栈**。前端 React 19 + TypeScript + Tailwind，后端 Node.js 20 + Express + Zod，数据层 PGlite（嵌入式 PostgreSQL）演示零依赖开箱即跑，生产一行环境变量切 PostgreSQL 16.15；AI 接阿里云百炼 DashScope（OpenAI 兼容模式）。这套栈**单机、双机、上云都能跑**，中小工厂最友好。"
- 追问应对："为什么不用 Java 那套？"→"我们是 Web 应用开发类参赛项目，JS 全栈一条链路交付最快、演示最稳；关键能力（状态机、乐观锁、迁移、备份）跟语言无关，是工程问题。"

**Q15｜PGlite 嵌入式数据库，撑得起工业系统吗？（高频打击题）**

- 话术："**PGlite 是演示形态**——嵌入式、零依赖、开箱即跑，跑的是标准 SQL。**生产形态通过 `DB_TYPE=postgres` 一行环境变量切换**到独立 PostgreSQL 16.15：适配器接口隔离 + 覆盖全部 30 张表的迁移工具 + 行数校验，已实证 25 个迁移零冲突（`docs/生产模式验证报告.md`，核心回归 15/15）。**存储可替换，业务闭环才是系统。**"
- 追问应对："PGlite 和 PG 的 SQL 兼容性怎么保证？"→"PGlite 就是 PostgreSQL 的 WASM 版本，方言 100% 兼容；唯一差异是不支持 pgvector 扩展，向量检索已预留 JSONB 降级路径，这在架构设计里就是预谋好的。"

**Q16｜数据量大了怎么办？**

- 话术："两条路都已备好：**①纵向**——切独立 PostgreSQL + 连接池（已实证）；**②横向**——架构里预留了 Redis 迁移路径，限流和登录防爆破当前是进程内实现，单副本够用；要水平扩容时先迁 Redis + 切 PG 再 `--scale`，README 里写了明确的升级路径和坑。这是**有意识取舍**：当前规模内存实现零依赖、零延迟，不为不存在的需求提前上复杂度。"
- 追问应对："内存实现多副本会失效？"→"对，文档里我们主动写明了：多副本时限流阈值等效放大 N 倍、防爆破失效。所以 README 明确警告先迁 Redis 再扩容——这恰恰说明我们对边界想清楚了，而不是藏着。"

**Q17｜数据丢了怎么办？**

- 话术："三层保险：**①每日 02:00 自动备份**（容器内 cron，保留最近 7 天）；**②手动备份脚本** `scripts/backup.sh`（Windows 有 ps1 版）；**③一键恢复脚本** `scripts/restore.sh`。生产叠加 PostgreSQL 原生备份策略。备份文件落盘可查。"
- 追问应对："恢复演练过吗？"→"恢复脚本和备份脚本配套验证过，属于我们固定的演示备选动作，现场可以跑。"

**Q18｜并发安全怎么保证？**

- 话术："工单操作三层防护：**①更新前比对版本号提前拦截**；**②SQL `WHERE version=?` 数据库级原子 CAS**；**③rowCount=0 时二次读取真实版本返回 409 + 当前版本**，前端弹窗提示刷新。选乐观锁是因为工单是低冲突场景，避免锁行的性能开销。专项测试 `tests/optimistic-lock-and-concurrency.test.ts` 整份覆盖并发冲突路径。"
- 追问应对："为什么不用悲观锁？"→"同一工单同时被两人操作的概率极低，悲观锁白付锁开销；冲突时让用户刷新重试是更符合工业现场的做法。"

**Q19｜工单状态机怎么设计的？**

- 话术："5 态有限状态机：**created → dispatched → in_progress → pending_acceptance → completed / cancelled**，completed 和 cancelled 是终态不可流出；pending_acceptance 可回退到 in_progress（验收不通过返工）。**非法跳跃一律拒绝**：created 不能直接跳 in_progress，必须先派单。状态流转全量写时间线，可追溯。专项测试 `tests/work-order-state-machine.test.ts` 覆盖。"
- 追问应对："为什么允许返工？"→"质检不通过就得让技师重新修，这是真实工业流程；但返工只有一条受控路径，不能绕回派单，安全上不放松。"

**Q20｜安全方面做了什么？**

- 话术："从外到内五层：**①全局 API 鉴权基线**——默认拒绝 + 白名单，没 token 一律 401；**②RBAC 细粒度权限**——9 类岗位账号各管一摊，越权写审计；**③登录防爆破 + 接口限流**——失败计数超阈值锁定，防撞库；**④X-Forwarded-For 防伪造**——默认只看 socket 真实 IP，代理头必须显式信任；**⑤攻击链回归测试**——把真实漏洞（任意 JWT 拖源码）写成永久测试用例，安全基线默认拒绝，`tests/auth-baseline.test.ts` 8 个用例。"
- 追问应对："等保三级是什么水平？"→"严格说我们是**参照等保三级规范设计的安全基线**——独立强密码、哈希存储、审计日志、权限分离这些都有；完整等保三级测评是合规咨询流程，不是软件功能，我们不作虚假声称。"

**Q21｜演示密码安全吗？**

- 话术："安全。9 个演示账号**各角色独立强密码**（≥15 位，大小写+数字+特殊符号），**Bcrypt cost=10 加盐哈希**入库，杜绝通用弱口令；内置首次登录强制改密策略，演示环境默认关闭保流畅，**生产环境必须开启**，密码经环境变量注入不落代码。"
- 追问应对："密码写文档里了，算泄露吗？"→"这是演示环境的公开演示账号，和测试数据一个性质；生产密码走环境变量，演示密码只存在于演示环境，README 有明确安全声明。"

**Q24｜说明书怎么生成的？是不是 AI 写的？**

**Q25｜部署怎么跑？评委想现场看。**

## 四、万能应对话术（答不上来 / 被追问 / 被质疑时）

**1. 遇到真不会的问题（诚实 + 迁移，绝不编）**
> "这个问题我们内部讨论过但没有深入验证，我先说目前确定的：……（讲你知道的一半）。具体到 X 这块我们证据还不充分，我可以讲下我们的设计思路……如果您需要，答辩后我可以把验证结果补给您。"
> **原则：宁可承认边界，不可现场编造。** 编造一旦被戳穿，全盘可信度崩。

**2. 被连环追问同一话题**
> "我把这个问题拆成三层回答：业务上……技术上……证据上……（然后选一层讲透）。"
> 用"拆三层"把话题拉回你准备好的结构，同时显得思路清晰。

**3. 被质疑"这不就是调 API / 就是模板 / 就是抄开源"**
> 固定回应："**对，工具是公开的，但把它组合成敢在产线上用、且每个环节可审计可验证的闭环，是我们做的。**"然后立刻指向证据（代码路径 / 测试 / 报告）。不要辩解，用证据说话。

**4. 被要求报"准确率 / 性能数字"这种你没测过的**
> "这个指标我们没有做过严格测量，**不报虚数**。我们可以现场演示/跑一下看效果，或者讲我们已有的评测记录。"（永远不编数字）

**5. 演示翻车（按钮点不动、页面报错）**
> "这个环节我们演示前调整过，我先说一下预期的效果……（讲功能设计），我们马上处理一下环境。" 态度稳住，把话题引导到"功能设计 + 证据"上，评委通常更在意你怎么应对而不是错误本身。

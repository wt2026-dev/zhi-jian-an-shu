## 一、架构选型

### Q1: 为什么用 PGlite 而不用 PostgreSQL？

**回答**：PGlite 是 WASM 版 PostgreSQL，零依赖、开箱即跑，确保评审环境无需预装数据库；生产模式已实证兼容 PG 16.15，切换只需改一行环境变量。

**证据**：
- 切换逻辑：`src/db/db.ts:156-220`（`DB_TYPE=postgres` 走 pg 连接池，否则走 PGlite）
- PG16 实测报告：`docs/生产模式验证报告.md`（23 个迁移零冲突、15/15 核心用例通过）
- 迁移工具覆盖 29/29 张表：`scripts/migrate-pglite-to-postgres.ts`

### Q2: 数据丢了怎么办？

**回答**：三层保险——每日 02:00 自动备份（保留 7 天）、手动备份脚本、一键恢复脚本。生产环境可叠加 PostgreSQL 原生备份策略。

**证据**：
- 自动备份：`docker-compose.yml` 中 cron 服务配置
- 备份脚本：`scripts/backup.sh`（Linux）、`scripts/backup.ps1`（Windows）
- 恢复脚本：`scripts/restore.sh`

### Q3: 9/12 数据事件是怎么回事？

**回答**：迁移重编号时本地嵌入式数据库文件锁残留导致启动异常。已修复：启动时自动清理异常 PID 锁文件，测试环境隔离为内存实例，事件归档于 `archive/` 供追溯。

**证据**：
- 自动清理逻辑：`src/db/db.ts:130-135`（`清理异常残留的锁定文件`）
- 测试隔离：`vitest.config.ts`（每个测试文件独立 PGlite 内存实例）
- 事件备份：`archive/backup/data-corrupt/`

## 二、AI 能力

### Q4: 20 项 AI 能力是真的吗？还是凑数？

**回答**：20 项按 `/api/v1/ai/*` 路由去重统计，每项对应真实接口。分三层：纯规则逻辑（4 项）、AI 生成（12 项）、多模态（4 项）。

- 能力分层说明：`archive/答辩防守话术-AI深度.md`（原始分层结论保留于 archive）

### Q5: AI 出错了怎么办？工业场景能信吗？

**回答**：三道防线——降级不伪造（`degraded` 标记）、人工审核闸（`ai_generation_reviews`）、回答带溯源（`knowledgeSources`）。AI 定位是辅助决策，不是替代判断。

**证据**：
- 降级机制：`src/server/services/aiClient.ts`（`handleAiRouteError` 函数，失败返回规则引擎结果）
- 审核闸表：`src/db/migrations/020_ai_generation_reviews.sql`
- 溯源输出：`src/server/services/knowledgeRetrieval.ts`（返回结果带 `knowledgeSources` 字段）

### Q6: 没网没 Key 会不会崩？

**回答**：不会。所有 AI 接口无 Key 时自动降级为规则引擎结果，页面正常显示、流程不中断。

**证据**：
- 降级测试：`tests/ai-verification.test.ts`（6 用例验证降级契约）
- 无 Key 行为：`tests/ai-features.test.ts`（离线模式全量测试）

### Q7: 视觉识别是自己做的吗？

**回答**：视觉模型调用阿里云 qwen-vl，但系统层（图片预处理、缺陷分类、结果落库、合规审计）是自研的。

**证据**：
- 视觉接口：`src/server/controllers/aiVisionController.ts`（调用 `DASHSCOPE_VISION_MODEL`）
- 结果落库：`src/db/repositories/aiAnalysisLogRepository.ts`
- 真实效果评测：`docs/AI真实效果评测报告.md`（15 条诊断 + 4 张视觉，实测日期 2026-09-14，100% 通过率）

## 三、安全与合规

### Q8: 演示密码安全吗？会不会泄露？

**回答**：演示环境各角色独立强密码（≥15 位，含大小写+数字+特殊符），经 Bcrypt（cost=10）加盐哈希存储；支持首次登录强制改密策略（演示环境默认关闭保流畅，生产必须开启）。

**证据**：
- 密码哈希：`src/server/services/authService.ts`（`bcrypt.hash` cost=10）
- 改密策略：环境变量 `DEMO_FORCE_PASSWORD_CHANGE`
- 密码表：`README.md` 演示账号表

### Q9: 权限控制是真的吗？

**回答**：7 种角色 RBAC 细粒度权限，全局 API 鉴权基线（默认拒绝 + 白名单），越权操作写入审计日志。

**证据**：
- 鉴权中间件：`src/server/middleware/auth.ts:7-43`（`requireAuth` + `requireRole`）
- RBAC 测试：`tests/rbac.test.ts`（11 用例覆盖 6 种角色越权拦截）
- 全局基线：`src/server/middleware/auth.ts:48-60`（`PUBLIC_API_EXACT` 白名单）

### Q10: 审计日志能追溯吗？

**回答**：全量操作审计，每次 AI 调用、降级、权限拒绝都有记录，admin 可查。

**证据**：
- 审计服务：`src/server/services/auditService.ts`（`addAuditLog` 函数）

## 五、业务价值

### Q15: 这个系统解决了什么痛点？

**回答**：工业检修现场三个核心痛点——纸质工单流转慢（3-5 天闭环）、经验依赖老师傅（新人无法独立诊断）、安全作业票审批脱节（线下签字 + 纸质存档）。系统用数字化闭环解决。

**证据**：
- 工单全流程：`src/components/WorkOrdersView.tsx`（创建→派单→接单→完工→验收）
- AI 诊断：`POST /api/v1/ai/diagnose`（故障诊断向导）
- 作业票管理：`src/components/SafetyManagementView.tsx`

### Q16: 知识沉淀怎么做的？

**回答**：AI 生成内容 → 人工审核闸 → 优质内容入库 → RAG 检索复用，形成"AI 输出→人类审核→知识积累→AI 再引用"的信任飞轮。

**证据**：
- 知识库表：`src/db/migrations/011_knowledge_base.sql`
- 向量 RAG：`src/db/migrations/015_knowledge_embeddings.sql`
- 审核闸：`src/db/migrations/020_ai_generation_reviews.sql`
- 混合检索：`src/server/services/knowledgeRetrieval.ts`（向量 + 关键词 RRF 融合）

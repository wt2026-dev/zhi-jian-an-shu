## 1. Part A：全局限流误伤（P0）

### 1.1 问题

`app.use("/api/v1/", globalLimiter)` 把**所有** `/api/v1/*` 请求计入同一个「每 IP 每分钟 240 次」的计数器。实测**一次页面加载就要打 35 个接口**，演示时快速切页/刷新会在 60 秒窗口内耗尽额度；一旦超限，所有接口一律 429，其中 `/auth/me`（会话恢复）失败会让页面直接跳回登录页 —— 现场表现与"程序崩了"无法区分，等窗口过去才自动恢复。

### 1.2 改动

**`src/server/middleware/rateLimit.ts`**

1. `createRateLimiter` 新增 `exemptPrefixes?: string[]`，白名单判定放在**计数之前**（既不累加计数，也不做窗口过滤，零副作用直通）。
2. 白名单匹配语义是「**精确路径 或 其子路径**」，不做裸字符串前缀匹配：

   | 请求 | 是否豁免 | 原因 |
   |---|---|---|
   | `/api/v1/auth/me` | ✅ | 精确命中 |
   | `/api/v1/auth/me?x=1` | ✅ | 带查询串 |
   | `/api/v1/auth/me/avatar` | ✅ | 子路径 |
   | `/api/v1/auth/members` | ❌ | **兄弟路由不得被静默豁免**（否则将来新增路由会出现"限流莫名失效"） |

3. 必须基于 `req.originalUrl` 判断：限流器挂在 `/api/v1/` 上，挂载后 `req.url` 已被剥离挂载前缀（只剩 `/auth/me`），拿它比对永远不成立。这一条由一个**真实 Express 挂载**的用例钉住，而不是靠注释。
4. 阈值与豁免：

   ```ts
   export const globalLimiter = createRateLimiter({
     windowMs: 60 * 1000,
     max: 600,                                  // 240 → 600（一次加载 35 个接口，留足快切余量）
     name: "global",
     exemptPrefixes: ["/api/v1/auth/me"],       // 会话恢复接口永不参与计数
   });
   ```

5. `authLimiter`（20/分钟，仅 `/login`）与 `aiLimiter`（60/分钟）**保持不变** —— 爆破防护与 AI 计费保护不受影响。

### 1.3 验证

**单元测试** `tests/rate-limit-sweep.test.ts`（13 项全绿），新增 8 项覆盖：

- 第 601 次请求 → 429；第 241 次 → 200（针对旧阈值 240 的反回归）
- 连续 900 次 `/auth/me` 全部放行，且**从未进入计数器**
- **真实 Express 挂载**场景下 600 次 `/equipments` → 429，随后 5 次 `/auth/me` → 200（证明 `originalUrl` 的必要性）
- `authLimiter` 仍为 20/分钟、`aiLimiter` 仍为 60/分钟
- `/api/v1/auth/members` **不**被豁免；子路径与带查询串的 `/auth/me` 被豁免

**端到端** `scripts/verify-ratelimit.mjs`（零第三方依赖，CDP 驱动真实浏览器）→ `ok: true`：

## 2. Part B：设备 3D 场景「单台特征化 + 实时分析」

核心诉求：*"16 个设备应该每一个都做得很具体，就像城市生成器里每个城市有它的特征一样……不要 16 台设备一锅端；要能对单台设备做实时分析。"*

### 2.1 B1：16 台设备的独立配方

**「词汇 vs 配方」分层**（参考生成器的 STYLES 思路）：

| 文件 | 职责 |
|---|---|
| `src/components/equipment3d/parts.ts` | **词汇**：几何构造器、色板角色、动画规格、可辨识旋转件 |
| `src/components/equipment3d/deviceProfiles.ts` | **配方**：16 份，每份只负责"挑词汇、摆位置、上涂装" |
| `src/components/equipment3d/equipment.ts` | 跨设备合并、批处理、动画驱动 |

每份配方含：`code`（设备编号铭牌）、`signature`（辨识特征描述）、`features[]`、`livery/livery2`（专属涂装）、`protoLabel`、`build()`。

**批处理粒度升级**是让"16 台全异构"与"低 drawcall"并存的关键：批处理键从"原型"改为 **`geometry.uuid | tint`**，因此每台设备可以完全独立建模，而共用的零件（法兰/底座/电机/指示灯）仍自动合并进同一个 `InstancedMesh`。实测 **434 drawcall / 35,206 三角面 / 43 个活动动画实例**。

**颜色纪律**：设备本体恒为 `status` 色（健康状态必须是最先被读到的信号），`livery/livery2` 固定不随状态变化 —— 因此设备在状态改变后依然可辨识。

### 2.2 B1 关键缺陷：旋转动画**看不见**

这是本轮最有价值的发现。原实现里所有 `spin` 零件都是**裸 `cylX` 圆柱绕自身轴旋转** —— 圆柱是旋转对称的，侧表面法线绕轴旋转不变，着色逐像素不变，**等于动画在跑但画面纹丝不动**。

修复：新增两个"可辨识旋转件"构造器，旋转件必须带**非对称特征**：

- `pushImpeller()` —— 轮毂 + 绕轴均布的叶片（风机/叶轮）
- `pushShaftKey()` —— 轴芯 + 偏心键块（轴/联轴器/螺杆转子）

叶片共用同一块 box 几何体与同一 tint，批处理后只多 1 个 drawcall。活动动画实例数因此从 **17 → 43**，而 drawcall 仅 421 → 434。

同时补上了两处"running 却完全静止"的漏配：

- **5# 多级锅炉给水泵**（running 88）：补上带键联轴器
- **15# 码垛机器人**（running 89）：补上带键腕部回转关节（10# 搬运机器人同步补齐，保持两台机器人一致）

### 2.3 状态驱动动画（无随机播放）

`animActive(kind, status)` 是**唯一**激活判据：

| 动画 | 激活条件 |
|---|---|
| `spin` / `slide` | 仅 `running` |
| `shake` | 仅 `fault` / `critical` |
| `blink` | `STATUS_META[status].alert`（预警黄闪 1.6 Hz / 故障 3.4 Hz / 紧急 4.6 Hz 脉冲） |

每帧只重写**已激活**实例的矩阵/颜色（43 个），并预分配 `Matrix4/Vector3/Color` 临时对象，做到零 GC。

### 2.4 B2：单台实时分析闭环

点击设备（或从右侧下拉选择）后：

1. 相机**平滑推近**：`focusDevice()` 只改轨道相机的**目标值**，由既有指数阻尼插值过去 —— 表现是"镜头推近"而不是"画面跳转"，与生成器切换城市的手感一致。
2. 右侧面板切到「设备分析」页签（与「场景参数」并列，符合"可切换标签页"的要求），展示：
   - 设备档案（`equipmentApi.getById`）
   - **实时遥测曲线**：轴温 / 振动 / 负载率 48 小时（`getTelemetryHistory(id, 48)`），自绘 canvas 折线 + 面积填充（不引图表库，避免给 3D chunk 再加几百 KB）
   - **AI 智能诊断**：**按钮触发**（避免每次点选设备都产生大模型计费），复用 `EquipmentHealthView` 的调用方式
   - 最近工单（`workOrderApi.list({ equipment_id })`）
   - 专属辨识特征卡片（配方 signature + 特征 chips + 涂装色块）

`handlePick` 的 `Promise.allSettled` 扩展为三接口并发。

**面板内不存在任何 `Math.random()` 或本地波形合成** —— 每个数字都来自后端接口。

### 2.5 B3：预设降级为「环境」

3 套预设（标准/重工/户外）只影响厂房环境（地面/柱网/光照/外壳/相机），**设备个体特征完全不受预设影响**（配方按设备 id 固定）。实测同一台设备在 3 套预设下 `signature` / `status` / `health` 完全一致。

### 2.6 严重缺陷：一个对象被当作 React child 渲染

端到端验收一度整体失败，`window.__e3d.canvas()` 返回 `null`，页面显示应用的错误边界：

> 页面渲染出现异常
> Objects are not valid as a React child (found: object with keys {required, level, reason, requiresConfirmation, riskTypes, degraded}).

根因：`/api/v1/ai/diagnose` 返回的 `safetyNotice` 是**对象**，而 `DeviceAnalysisPanel` 把 state 声明成 `string | null` 后直接 `{aiSafety}` 渲染。`await res.json()` 的类型是 `any`，**tsc 完全拦不住**；不渲染就碰不到，**单测也拦不住**。错误边界把整棵子树卸载，3D 画布与设备下拉框一起消失，表现为"页面崩了"。

修复：类型化为 `AiSafetyNotice`，并抽出 `src/components/equipment3d/aiDiagnosis.ts`（不依赖 three.js/React，可被 node 环境单测直接导入）统一归一化；渲染侧只取 `reason` / `riskTypes` / `degraded` 等标量字段。

## 5. 未达标 / 环境受限项（如实报告）

1. **帧率 20–22 fps（门槛 ≥45）** —— 验证机**无 GPU**，浏览器上报渲染器为
   `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver)`，
   即 **CPU 纯软件光栅化**，所有三角形/着色器/阴影都由 CPU 计算。
   本场景负载仅 **35,206 三角面 / 434 drawcall**，对任何独显/核显都属极轻量。
   已内置三档画质与三角面预算供低配机器降级。**建议在带 GPU 的机器上复测帧率，本报告不伪造该数字。**
2. **首次预设切换 78.9 ms 贴近 80 ms 门槛** —— 该数值包含页面加载后的**一次性**着色器编译与贴图上传；
   同一轮内后续切换为 41.4 / 32.5 ms，纯几何重建 17.8 ms。
   历史测量中冷启动曾达 424 ms、稳态 27–31 ms，结论一致：**冷启动成本 ≠ 稳态重建成本**。
3. **内存未单独测量** —— 本轮未做内存基线对比，不作结论。
4. **11# 板式换热器在 running 态下无动画** —— 该设备物理上**没有旋转件**（板片组 + 接管 + 框架），
   因此不装旋转动画。这是刻意保留的物理正确性，而非漏配。
5. **像素差分无法证明"单台设备在动"** —— 厂房里有一台**常动的行车**（`scene.ts` 的 `craneT` 持续推进），
   它是否落在取景框内取决于机位角度。实测同一脚本两次运行，待机与故障的"画面变化量"排序会**翻转**，
   足以说明该方法无法隔离单台设备动画。因此该项**已从通过判据降级为诊断性数据**，
   "状态驱动动画"改由确定性单测覆盖（`animActive` 全状态映射 + 装配级断言：旋转件必须带非对称特征、
   5#/15# running 确有运动、14# standby 完全静止）。
6. **"16 台两两可辨"不能只靠自动化代理指标，已补做人工高分辨率复核。**
   脚本里的 `allDistinct: true` 用的是**整幅画布**的 12×8 指纹 —— 它把背景（地面、光晕环、立柱、
   机位角度）一起算进去了，**两台设备即使长得一样，只要机位不同也能"通过"**。
   为排除这个假阳性，另用 Pillow 裁出**只含设备本体**的区域重算两两距离，结果同样不可信：
   距离被共有的地面/光环主导，连"机器人 vs 箱体"（115 vs 116）这种肉眼完全不同的组合都被排进"最相似"。
   **结论：两套代理指标都不成立，最终以人工复核为准。**
   人工复核方式：把 16 张截图裁出设备本体拼成 `contact-sheet-16-devices.png`，并对同族设备做高分辨率
   并排对比（`group-motors-104-108-114.png` / `group-cylinders-106-112-113.png` / `group-boxes-102-107.png`）。
   复核结论：**16 台在形态与色相上均可区分**。同族设备靠"形态 + 色相"双重区分，例如三台电机：
   4# = 绿色本体 + **7 道蓝色散热翅片环** + 顶部接线盒；8# = 绿色本体（**无翅片**）+ **尾部励磁机小圆柱**（teal 色阶差）；
   14# = **整体待机灰** + 冷却风罩。三台压缩机/泵：6# = 灰紫本体 + 竖向大接管；12# = 故障红高亮；13# = teal 本体 + 竖向油分离器。
   两台箱体：2# = 绿色百叶箱体；7# = 灰蓝箱体 + 大直径黑色输出法兰盘。

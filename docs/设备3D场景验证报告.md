## 1. 版本与 API 差异记录（硬约束要求）

> 约束原文：*"若实现中遇到 three 版本 API 差异（生成器用 r160，npm 安装可能更新），以实测为准适配，记录版本号。"*

| 项目 | 生成器（参考资产） | 本项目（实测） |
|---|---|---|
| three 版本 | r160（`index.html` importmap，CDN/本地 vendor） | **`three@0.186.0`**（npm 本地依赖，无 importmap） |
| 类型声明 | 无 | `@types/three@0.186.0`（`devDependencies`） |
| 引入方式 | `<script type="importmap">` + 相对路径 ESM | Vite 打包 ESM `import * as THREE from 'three'` |

### 1.1 实测到的 API 破坏性变更

**(1) `THREE.PCFSoftShadowMap` 的实现已在 r186 被移除。**

- 现象：控制台报 `THREE.WebGLShadowMap: PCFSoftShadowMap has been removed. Using PCFShadowMap instead.`
- 陷阱：该常量**仍然导出**（`three.core.js` 与 `@types/three` 均存在），因此 `tsc --noEmit` **不会**报错，属于纯运行时问题——与第九轮 `require()` 崩溃同类。
- 适配：`scene.ts` 直接使用 `THREE.PCFShadowMap`，并在代码中留注释说明原因：

```ts
// three r186 已移除 PCFSoftShadowMap 的实现（保留常量但会告警并回退），
// 这里直接使用 PCFShadowMap，避免控制台出现 "has been removed" 警告。
this.renderer.shadowMap.type = THREE.PCFShadowMap;
```

- 验证：修复后全量运行中该告警**已彻底消失**（见 `verify-result.json` 的 `errors.console` 为空数组）。

**(2) `PMREMGenerator` 必须复用，否则每次重建都触发着色器重编译。**

- 生成器的 `CityScene` 在每次 `build()` 里 `new PMREMGenerator(...)` 再 `dispose()`。
- 在 r186 + 软件光栅化下，新建 PMREM 会重新分配内部材质并触发着色器重编译，**单次实测约 1.3 s**；加上每次重建都销毁/重建阴影贴图，导致重建耗时 **1100–1800 ms**，远超 80 ms 门槛。
- 适配：PMREM 实例、环境贴图（按 `presetId` 缓存）、天空几何体、阴影贴图（仅在 `mapSize` 变化时重建）全部改为可复用/可缓存：

```ts
/** PMREM 生成器必须复用：每次 new 都会重新分配内部材质并触发着色器重编译，
 *  在软件光栅化下单次可达 1.3 秒（实测），复用后仅首次付出该代价。 */
private pmrem: THREE.PMREMGenerator | null = null;
```

- 效果：重建耗时从 **1100–1800 ms 降到 15–46 ms**（约 40 倍）。

**(3) `renderer.info.render.calls` 反映的是"上一帧"。**

- 首次 `build()` 后读取得到 0。改用自实现的 `countDrawables()`（遍历可见 Mesh 统计），并把不可见拾取代理排除在外。

> 以上三项均为**实测发现并适配**，不是照搬生成器代码。

## 3. 架构移植说明（生成器 → 本项目）

沿用生成器"**管线 + 配方**"的核心思想，把"城市"换成"工业厂房与设备台账"：

| 生成器概念 | 本项目对应实现 | 保留/改造 |
|---|---|---|
| 预设 = 完整配方（地形/配色/形态/布局/光照/相机） | `ScenePreset`：地面/配色/厂房/形态/布局/光照/相机 | **保留**，配方从"城市风格"换为"车间形态" |
| 确定性 PRNG（同种子同结果） | `rand.ts` 逐行移植，含 32 位整数溢出告警注释 | **保留**（不改算法，保证同种子可复现） |
| 高度场地形 + 裙边 | `Hall.reliefAt()` + 逐顶点着色地面；户外场站有真实微起伏 | 改造为地面/场地 |
| 建筑体块生成 | 8 类设备原型程序化建模（泵/压缩机/齿轮箱/减速机/电机/数控机床/机器人/换热器/配电柜/通用） | **改造**为设备建模 |
| 道具批渲染（`Batcher`） | `props.ts` 按 `(geometry, material)` 聚合为 `InstancedMesh` | **保留** |
| 手写阻尼轨道控制 | 球坐标 + 临界阻尼跟随 `k = 1 - Math.exp(-dt * 9)`；左键旋转/右键平移/滚轮缩放/双指捏合 | **保留**（交互手感与原生成器一致） |
| 着色器天空穹顶 + 雾 | `ShaderMaterial`（`BackSide`、`depthWrite: false`）+ `FogExp2` | **保留** |
| 共享几何缓存（`userData.shared` 守卫） | 模块级 `GEO_CACHE`，`disposeGroup()` 跳过共享几何 | **保留**（否则第二次重建会因释放复用几何而白屏） |
| 俯视小地图（`minimap`） | `EquipmentScene.drawMinimap()`：厂房轮廓 + 设备圆点（按真实状态着色）+ 相机位置与视锥 + 选中环 | **保留并改造**（详见 §5.3） |
| — | `InstancedMesh` 两级批渲染 + 逐实例状态色 | **新增**（生成器无"按业务状态着色"需求） |
| — | 状态光晕环 + 告警光柱 + 拾取代理 + 三角面预算自动降级 | **新增** |

### 3.1 状态可视化（核心卖点）实现

状态 → 颜色映射（`equipment.ts` 的 `STATUS_META`）：

| 状态 | 颜色 | 语义 | 是否告警 |
|---|---|---|---|
| `running` | `#27c46b` 绿 | 正常 | 否 |
| `warning` | `#f2c327` 黄 | 预警 | **是** |
| `fault` | `#e03b2f` 红 | 故障 | **是** |
| `critical` | `#ff4a1f` 橙红 | 紧急 | **是** |
| `overhauling` | `#2f8fe0` 蓝 | 检修中 | 否 |
| `standby` | `#8f9aa6` 灰蓝 | 待机 | 否 |
| `scrapped` | `#596069` 深灰 | 已报废 | 否 |
| `nodata` | `#9aa0a6` 灰 | 无数据 | 否 |

- **设备本体颜色**：以厂房钢材基色为底，向状态色 `lerp` 0.62（无数据 0.42），使设备既保持金属质感又能一眼读出状态。
- **状态光晕环**：地面环（`ring`），直接使用状态色，远距离也能判读。
- **告警光柱**：仅 `alert` 状态（预警/故障/紧急）生成竖向光柱，用于快速定位异常设备。
- **图例**：面板左上角显示 8 类状态及**实时计数**，与后端返回严格一致。
- **容错**：`statusKey()` 大小写不敏感、支持别名（`ok/normal/healthy`、`warn`、`alarm/error/broken/down`、`maintenance/repair/overhaul`、`idle/offline/stopped`），未知值一律归为 `nodata`（**不猜测、不伪造**）。其中 `critical` 实际**不在**前端 `EquipmentStatus` 联合类型内，代码显式兼容。

### 3.2 数据来源

- 复用既有 API 客户端 `src/api/index.ts`：`equipmentApi.list()` / `getById()`、`workOrderApi.list({ equipment_id })`。
- 鉴权沿用既有登录态 token，**未新增任何鉴权旁路**。
- 三级数据模式：`api`（正常）→ `cache`（接口失败时回退到 `useAppData()` 已缓存数据，并显示琥珀色提示条）→ `empty`（空态卡片 + 重试按钮，明确说明不会随机模拟状态）。
- 点选信息卡用 `Promise.allSettled` 并发取"设备详情 + 该设备工单"，任一失败则用本地数据兜底并在卡片内提示，**不会白屏或抛异常**。

### 4.4 相机取景修正

原实现按预设 `camera.distance`（118）配合"包围球"计算距离，而车间是**宽而扁**的体量，导致厂房只占画面约 15%，大量留白。改为**水平/垂直双向独立取景**：

```ts
const vHalf = (this.camera.fov * Math.PI) / 360;
const hHalf = Math.atan(Math.tan(vHalf) * Math.max(0.4, this.camera.aspect));
const halfW = Math.hypot(hall.bounds.halfX, hall.bounds.halfZ) * 0.86;
const halfH = Math.max(6, hall.structureHeight) * 0.5;
const dH = halfW / Math.tan(hHalf);
const dV = halfH / Math.tan(vHalf);
const k = clamp(preset.camera.distance / 120, 0.8, 1.4);
return Math.max(dH, dV) * 1.3 * k;
```

预设的 `distance` 从"绝对距离"降级为 0.8–1.4 的**风格系数**，既保证主体充满画面，又保留各预设的取景差异。

### 6.3 帧率（门槛 ≥30 fps）—— **环境受限，如实报告**

| 场景 | 实测帧率 |
|---|---|
| 三套预设 | 20–21 fps |
| 三档画质 | 均 20 fps |

**这不是代码缺陷，而是验证机没有 GPU。** 浏览器上报的渲染器字符串：

```
ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)
```

- `SwiftShader` 是 **CPU 软件光栅化**实现，所有三角形、着色器、阴影全部由 CPU 计算。
- 设备像素比 `dpr = 1`，画布 CSS 尺寸 `1388×608`。
- 三角面仅约 3.2 万、drawcall 200–375，**这个负载量对任何独显/核显都是极轻量的**（通常轻松超过 60 fps）。

**结论表述**：帧率指标"未达标"的原因是验证环境无图形硬件，属环境上限；渲染负载（3.2 万三角面 / 333 drawcall）处于极低水平，且已内置三角面预算（流畅 12 万 / 均衡 26 万 / 精细 52 万）与画质档位供低配机器降级。**建议在具备 GPU 的机器上复测帧率**，本报告不伪造该数字。

### 6.4 内存与资源释放

- 组件卸载时完整释放：`cancelAnimationFrame`、移除全部事件监听（含具名化的 `onContextMenu`）、`disposeGroup()` 释放自有几何/材质（跳过 `userData.shared` 共享几何）、天空几何/材质、光照、`envRT`、`pmrem`、`scene.environment = null`、`renderer.dispose()`、移除 canvas。
- React StrictMode 双挂载幂等：挂载时先清理容器内残留 canvas，再初始化。
- 已修复 `setPointerCapture` 在合成事件下抛 `NotFoundError` 导致交互中断的问题（加 `try/catch`，不影响旋转/平移）。

### 7.3 验证过程本身的两个工程问题（已修）

自动化验收跑不起来时，先怀疑验证环境而不是应用代码。本轮就遇到并修掉了两个**验证侧**问题：

**(1) 写截图会触发整页重载，把验收流程打断。**
Vite 开发服务器默认监视整个工程目录，而验收脚本把截图/结果写到 `docs/equipment3d-shots/`——
每次写文件都会触发一次 HMR 整页重载，清掉注入的辅助对象并把会话打回登录页。
现象是"偶发失败"（前几次运行靠时序侥幸通过）。
修法两层：① `vite.config.ts` 增加 `server.watch.ignored`（去掉根因，纯开发配置）；
② 验收脚本加入**会话自愈** `ensure3DView()`：检测到被重载打断就自动重新登录并回到 3D 视图。
实测生效——本轮 `enter-3d-view` 的结果是 `ok (attempt 2)`，即**确实被重载打断过一次并自动恢复了**。

**(2) 401 被误判成应用错误。**
未登录时应用会探测当前会话（`GET /api/v1/auth/me`），返回 401 是**正确行为**（随后展示登录页）。
它一度被计入"真实控制台错误"导致验收判负。已在错误分类中显式归入"既有且预期内的噪声"，
并写清理由——**分类必须能解释每一条为什么不算问题，否则报告不可信**。

> 这两条也解释了为什么"错误分类"要分四类而不是简单地把 console 里的东西一锅端：
> 既有噪声 / 工具自身产物 / 验证手段主动制造 / 真实缺陷，四者性质完全不同。

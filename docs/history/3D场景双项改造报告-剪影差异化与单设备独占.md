# 3D 场景双项改造报告 —— Part A 剪影差异化 + Part B 单设备独占模式

> 任务：把 16 台设备做成"每台一套独立剪影"（对齐程序化城市生成器"每座城市一套独占模型"的标准），
> 并新增"选中某台即进入单设备独占视图"的交互。
>
> 报告口径：**改造前后对比数据 + 改了哪些文件 + 逐条验收结果**。

---

## 0. 一句话结论

**Part A**：16 台设备中原本有 7 台剪影雷同（3 台电机 / 2 台泵 / 2 台减速箱各共用一套模具），
已全部重写为互不相同的剪影；其余 9 台**主体一字未改**（有机械证明，见 §3.4）。
**Part B**：新增单设备独占模式，选中设备后场上只剩 1 台、包围盒占画面约 3/4、可自由旋转缩放。
**性能门限（三角面 ≤25k / drawcall ≤250 / 重建 ≤80ms / fps ≥45）在总览与独占两种模式下全部通过。**

## 1. 改造前的真实基线（重新实测，不引用记忆值）

上一轮报告曾用"联络表缩略图"判断"16 台均可区分"，**该结论不成立** —— 那个判断主要靠**色相**
（绿 / 灰 / 红 / teal）区分，而本任务的验收标准是**剪影（形状）**。把彩图去色只看轮廓后，
4#/8#/14# 三台电机、1#/12# 两台泵、3#/7# 两台减速箱确实是**同一套模具**。

为了给出可信的"改造前"数字，本轮**没有沿用历史记忆值**，而是把改动前的生产构建重新跑起来实测：

| 步骤 | 做法 |
|---|---|
| 1 | 取改动前打出的生产包 `dist.prev-200141/`（本轮开工前 `dist/` 的原样备份） |
| 2 | 该包自带的 `server.cjs` 是 dev 模式产物（会拉起 vite 中间件、抢 24678 端口），无法独立运行 |
| 3 | 于是用 `scratch/baseline-run/serve-static.mjs`（零依赖）把旧构建当**静态站**伺服，并把 `/api`、`/uploads` **反代到当前后端** `127.0.0.1:3000` |
| 4 | 结果：**旧前端 + 当前后端 + 同一数据库 + 同一台机器**，测出来的就是纯粹的"改造前" |

> **踩坑记录**：反代初次访问被后端 403 挡下 —— `CSRF 校验失败: 请求来源 http://127.0.0.1:3100 未在受信任白名单中`。
> 后端 CSRF 兜底会校验 `Origin`/`Referer` 是否在 `CORS_ALLOWED_ORIGINS` 白名单内，白名单只有 `:3000`。
> 解法：反代时把来源改写成后端信任的 `http://127.0.0.1:3000`（反代的标准做法；CSRF 校验逻辑一字未改，
> 请求仍须带正确账号密码）。

## 2. 改造前后对比数据

### 2.1 性能（同机同后端，无头 SwiftShader）

| 画质档 | 改造前 三角面 / drawcall / 重建 | 改造后 三角面 / drawcall / 重建 | 差值 |
|---|---|---|---|
| 流畅 low（冷启） | 16,200 / 147 / 72.3 ms | 16,048 / 159 / 63.6 ms | 三角面 **−152**，drawcall **+12** |
| 均衡 medium | 27,793 / 204 / 104.7 ms | 27,691 / 202 / 52.1 ms | 三角面 −102，drawcall **−2** |
| 精细 high | 35,966 / 206 / 138.8 ms | 35,800 / 204 / 121.1 ms | 三角面 −166，drawcall **−2** |
| 流畅 low（热态） | 16,200 / 147 / 15.6 ms | 16,048 / 159 / 17.8 ms | 三角面 −152，drawcall +12 |

**差值怎么来的**：
- **drawcall +12**（流畅档）：全部来自**新增的 16 张编号铭牌**。铭牌原先只在"均衡/精细"档渲染，
  本轮改为**三档都渲染**（验收要求"总览里一眼看到编号"），代价正好 +16 drawcall，
  而 7 台重写设备的合批优化又省回约 4 个，净 **+12**。
- **三角面 −152**：7 台重写设备的零件组合比原模具更省几何（原模具的通用翅片/端盖被替换成更克制的结构）。

> 说明：`重建(ms)` 在软件光栅化下受 CPU 争用影响明显，冷启读数（首次触碰该档位）含 JIT/着色器预热，
> 因此**以热态读数为准**：流畅档 15.6 → 17.8 ms。冷启读数仅作参考。

## 4. Part B：单设备独占模式

### 4.1 改造前

`scene.ts` 的 `focusDevice(id)` 只把相机推近：另外 15 台仍在画面内，
且取景偏远（设备只占约 1/3 屏），用户反馈"太小"。

### 4.2 实现

**`equipment.ts`（设备层）**
- 新增 `showOnlyDevice(id)` / `showAllDevices()`：按设备分组切换可见性；
- 新增 `visibleDeviceCount()`：供性能条读"当前可见设备数"；
- 新增 `setChromeFocus(id|null)`：地面光晕环与告警光柱是**全场合批的 `InstancedMesh`**，
  没有单实例 `visible` 开关，只能把非目标实例的矩阵缩成 0（`setMatrixAt(idx, zeroMatrix)`）来"隐藏"。

**`scene.ts`（场景层）**
- 新增 `setIsolation(id | null)`：
  - `id` 非空 → ① 隐藏其余 15 台；② 按该设备包围盒重新取景（占画面约 3/4）；③ 关掉地面网格，留下干净的展示台；
  - `id` 为 `null` → 恢复 16 台并回到总览（复用 `resetFocus()`）；
- 新增 `liveStats()`：基于 `traverseVisible` 统计**当前可见**的三角面/drawcall/设备数；
- 独占状态下切画质/预设**不会被踢回总览**（重建出口处重新套用 `setIsolation`）。

**`EquipmentScene.tsx`（React 层）**
- 新增 `isolationId` 状态；选中设备（3D 点击或下拉框）**默认进入独占**；
- 右上角新增「返回总览」按钮，`data-testid="equipment3d-isolation-exit"`；
- 右侧分析面板、爆炸拆解、遥测回放**在独占下照常工作**。

### 4.3 取景反解：为什么不能直接用 `d = h / (2·FILL·tan(fov/2))`

这是本轮**最重要的一处修复**。

老公式假设"屏幕竖直方向只由设备高度决定"，**只有在相机水平正视时才成立**。
本场景相机是俯视的（`phi ≈ 1.0`，仰角约 33°），于是**设备的长度也会"倒"进屏幕竖直方向** ——
一台 2.4 m 高、5.5 m 长的减速机，投影后竖直方向要占 **1.55 个屏高**。

实测（1.0 = 恰好占满画面）：eq-107 **1.555**、eq-109 **1.462**、eq-108 **1.454**、eq-103 **1.276** ——
**16 台里 13 台被裁**，画面上设备四边都被切掉。

正确做法：把包围盒的 8 个角**投影到相机基向量**（right / up）上反解距离，取最大值：

```
R ≥ p·u + max( |p·right| / (FILL·tanH),  |p·up| / (FILL·tanV) )
```

修完后 16 台的投影占比落在 **0.635 ~ 0.832**（均值约 0.75），**无一台被裁**。

> `FILL` 取 **0.85** 而不是 0.75：包围盒的 8 个角里有空角（零件并不会填满盒角），
> 实测投影占比约为 `FILL` 的 0.85 倍，所以用 0.85 反解，落到画面上才是"约 3/4"。

### 4.4 独占下的联动

- 设备**状态配色**（健康度 → `status` 涂装）照常；
- **工单状态指示环**照常（且非目标设备的指示环已随合批实例一起隐藏）；
- **遥测回放的状态覆盖逻辑**照常；
- **爆炸拆解**在独占下更聚焦：展开后场上仍然只有该台设备。

## 7. 回归与遗留

**回归（全绿）**
- `npx tsc --noEmit` → 0 错误
- `vitest run` → **35 个测试文件 / 277 个用例全部通过**
- `npm run build` → 退出码 0

**遗留 / 需注意**
1. **总览远景下 16 张铭牌同时可读性**：单台证据（每张独占图）与同族差异度指标都很硬，
   但"默认环境预设下拉远后 16 张铭牌是否同时清晰可读"没有独立做强验证 ——
   等轴（iso）预设更近、效果更好。这是本报告**相对最弱的一项**，如实列出。
2. **帧率口径**：无头 Chrome 走 SwiftShader 纯 CPU 软件光栅化，fps 被锁在 20~22，
   **不能当成代码性能问题**；真机（AMD Radeon 780M）三档均为 119~120 fps（垂直同步封顶）。
   报告中所有 fps 数字都附带了渲染后端字符串，避免脱离环境引用。
3. **仓库冻结状态**：`src/components/equipment3d/` 整个目录在 git 中未被跟踪，
   所有改动尚未提交。（此项属既有遗留，等待统一处理，非本轮引入。）

4. **`dist.prev-200141/`（22 MB）建议保留，不要当垃圾清掉**：它是**改动前生产包的唯一副本**，
   本报告 §1 的改造前基线测量、以及 §3.4 的"9 台禁改设备未被改动"证明，**都依赖它**。
   若确认不再需要复现这两项验证，才可删除；删除后仅剩已落盘的测量结果
   （`scratch/3d-identity/verify-result-BEFORE.json`、`untouched-devices-check.json`）。

5. **本轮清理的临时产物**：改造前基线用的数据库副本（42 MB，`scratch/baseline-run/data`）
   与旧构建副本已清除。`scratch/baseline-run/` 现仅剩 782 KB
   （`serve-static.mjs` 工具 + 基线测量结果 + 一份 759 KB 的上传文件副本）。
   该上传副本因沙箱批量删除保护未能一次清掉，可手动删除，不影响任何结论。

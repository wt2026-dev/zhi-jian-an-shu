# docs/ 目录索引与文档分级

> 建立于 2026-10-17。此前 `docs/` 看不出哪份是**现行口径**、哪份是**一次性历史记录**——
> 这正是"文档通胀"的表现。本文件不删除任何内容，只做**分级 + 索引**：先分清哪些还必须维护，再谈删减。
>
> 规模实测：**64 份 md**（顶层 47 份平铺 + 子目录 17 份）、约 37 MB（含 75 张截图与 12 个 `.slide` 源文件）。
> 下面 A–E 覆盖顶层 47 份；子目录见 F 节。

## 分级口径

| 级别 | 含义 | 维护责任 |
|---|---|---|
| **A 现行口径** | 描述**当前**系统事实（表数/用例数/AI 能力数/指标/团队分工）。代码或数字一变，必须同步改 | 改代码的人 |
| **B 现行方案** | 设计与演进方向，仍然有效，允许随实现更新 | 方案提出者 |
| **C 历史记录** | 某次修复/验收的**当时**快照。**不回填、不改数字**（数字类行请加 `<!-- 口径历史快照 -->`） | 不再维护 |
| **D 答辩材料** | 面向评审的讲稿/问答弹药，随答辩稿版本维护 | 答辩主讲 |

> ⚠️ **C 类的数字是历史，不是现状。** 引用前先看 `README.md`（唯一真源）或跑 `npm run metrics:check`。
> 行级标记 `<!-- 口径历史快照 -->` 会被 `scripts/check-metrics.mjs` 跳过校验，`--fix` 也不会改写它。

## 已知不一致（如实记录，未擅自改动）

1. **作者署名**：`git log` 里 150+ 次提交只有两个身份（`industrial-ops-dev` / `wt2026-dev`），
   而 `开发过程与团队分工口径说明.md` 描述的是多人分工。若确为多人协作，应让真人署名；
   若为多 AI 会话并行，该文档应如实写明"提交身份为会话占位名"。**这是对外口径问题，需负责人拍板**，
   本文档不做单方面改写。
2. **文档体量**：顶层 47 份 md 里 23 份属于 C 类（修复/验收/专项/测试记录），即**近一半是一次性记录**。
   它们对答辩有证据价值，但对后来者是噪声。建议下一步（需负责人批准）：
   - C1/C2/C3 合并为 `docs/history/`，并在文件名保留日期；
   - 重复的"第二轮/第三轮"报告合并为一份时间线；
   - 删掉 E 节那 6 份与 `archive-notes/` 重复的顶层副本；
   - 新增报告前先问一句："它会被引用第二次吗？" 不会 → 写进 `CHANGELOG.md` 的一个条目即可，不必新开文件。
3. **数字类文档的时效**：C 类报告里的"N 个测试文件 / M 个用例"是**当时**的快照。
   引用前先看 `README.md` 或跑 `npm run metrics:check`。

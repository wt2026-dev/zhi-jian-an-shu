# 答辩防守话术：存储选型（PGlite 可靠性）

> 用途：应对"嵌入式数据库撑得起工业系统吗 / 你们数据坏过吗 / 数据丢了怎么办 / 为什么不用真 PostgreSQL"类提问。
> 原则：**不回避、不狡辩**——把"演示选型"和"生产路径"分开讲，承认边界，展示完整的兜底设计。
> 所有说法均有代码支撑（src/db/db.ts、scripts/backup.sh、scripts/migrate-pglite-to-postgres.ts、docker-compose.yml）。

---

## 一、30 秒主话术（背诵版）

> "存储选型我们分两层：**演示层**和**生产层**。
> 演示环境用 PGlite——它是 PostgreSQL 的嵌入式实现，跑的是标准 SQL，不是玩具；选它是因为比赛和演示环境不确定、可能离线，我们要保证系统**开箱即跑、零外部依赖**。
> 生产层我们预留了完整切换路径：所有数据访问都走数据库适配器接口，**DB_TYPE=postgres 一键切换**到独立 PostgreSQL，配套了 PGlite→PostgreSQL 的数据迁移工具和行数校验；
> 数据安全上有**每日 2:00 自动备份、保留最近 7 天、一键恢复**。
> 我们答辩的原则是：不回避 PGlite 的边界，把演示选型和生产路径分开讲清楚。"

## 二、15 秒极简版

> "PGlite 是给演示的——嵌入式、零依赖、开箱即跑；生产走 DB_TYPE=postgres 切真 PostgreSQL，迁移工具和行数校验都备好了，每日自动备份 + 7 天保留兜底。"

---

## 三、选型逻辑：为什么演示用 PGlite（评委视角）

| 维度 | 说明 |
|---|---|
| 开箱即跑 | 无外部数据库依赖，评委环境离线也能跑通全流程 |
| 标准 SQL | PGlite 是真实 PostgreSQL 引擎（WASM 版），29 张业务表、事务、JSONB 全部原生支持 |
| 部署体积 | 嵌入式，Docker 单容器，无需编排数据库服务 |
| 适配器隔离 | `src/db/db.ts` 定义 DatabaseAdapter 接口，业务代码不感知底层实现，切换成本极低 |

**主动承认的边界**：PGlite 是单进程嵌入式存储，不具备独立 PostgreSQL 的多连接高并发、流复制、故障转移能力——所以它定位"演示/开发"，不冒充"生产"。

---

## 四、生产切换 PostgreSQL 路径（已有工具，可直接演示）

```
1. 目标库准备：独立 PostgreSQL 服务，建库 industrial_maintenance
2. 配置 .env：
   DB_TYPE=postgres
   DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD（或直接 DATABASE_URL）
   DB_POOL_MAX=10（连接池上限）
3. 数据迁移（一键）：
   npx tsx scripts/migrate-pglite-to-postgres.ts
   —— 自动执行全部迁移 SQL 建表 → 逐表批量迁移 → 输出"源行数 vs 目标行数"校验报告
4. 启动验证：npm run start，/health 确认数据库连接
```

**代码证据**：
- `src/db/db.ts`：`DB_TYPE=postgres` 创建 `pg.Pool` 连接池（connectionTimeoutMillis=5000，max 可配）；生产环境（NODE_ENV=production）**默认走 postgres**，未配置时按 DATABASE_URL 自动判断。
- `scripts/migrate-pglite-to-postgres.ts`：迁移 + 行数校验报告。
- **注意**：迁移脚本当前只覆盖 12 张核心表（users/equipments/work_orders 等），答辩前建议确认剩余表是否需补入脚本——评委可能追问这一点。

## 五、备份与恢复（数据安全三板斧）

| 措施 | 实现 |
|---|---|
| 每日自动备份 | 容器内 cron 每天 02:00 执行 backup.sh，打包数据目录为 tar.gz（带时间戳） |
| 保留策略 | 自动保留最近 7 天，过期备份自动清理 |
| 手动备份 | `bash scripts/backup.sh`（Windows：`powershell -File scripts/backup.ps1`） |
| 一键恢复 | `bash scripts/restore.sh backups/<备份文件>` |

## 六、9/12 数据事件复盘口径（诚实版）

> **先说结论**：开发期确实发生过一次本地数据目录异常，根因是**本地嵌入式库的进程锁残留 + 迁移脚本重编号操作**，不是 SQL 或业务代码缺陷。已从三方面修复并加入回归防线。

**证据链**：
- 事件现场数据目录已于 2026-09-13 压缩归档：`archive/backup/data-corrupt/industrial_ops_pg.corrupt-20260912-195755.tar.gz`、`archive/backup/data-corrupt/industrial_ops_pg_corrupted_20260912.tar.gz`（原目录已移出交付路径 data/，可解包复核）；
- `archive/backup/backups/migration_renumber_20260912/`（当日迁移重编号前的数据备份）；
- `src/db/db.ts` 启动逻辑：**自动清理异常的 postmaster.pid 锁定文件**（"已清理异常残留的锁定文件"）；
- `src/db/db.ts` 测试逻辑：**测试环境改用内存 PGlite，每测试文件独立实例**，注释明确写道——避免"postmaster.pid 互删/文件锁竞争导致的随机 500"。

**复盘口径（答辩背诵版）**：
> "9 月 12 日我们在做迁移脚本重编号时，本地嵌入式库出现了一次文件锁残留导致的启动异常。我们做了三件事：
> ① 启动时自动清理异常 pid 锁文件；
> ② 测试环境隔离为内存实例，杜绝共享目录的文件锁竞争；
> ③ 事件现场完整备份保留在 archive/，作为复盘依据。
> 这也让我们把'每日自动备份 + 7 天保留'提前加进了交付版本。对参赛演示环境来说，这类问题暴露得越早越好。"

> ⚠️ 团队确认项：事件当日是否还有其它操作（如并发启动多个实例、强制 kill），答辩前与当时操作人核对一遍细节，确保口径一致。

## 七、评委追问拆解

### Q1：嵌入式数据库撑得起"工业系统"四个字吗？

**回答**：
"撑不起生产，所以我们没让它撑。我们的分层是：**演示/开发用 PGlite（零依赖、开箱即跑），生产用独立 PostgreSQL（适配器 + 迁移工具 + 校验报告）**。'工业系统'体现在业务闭环和安全合规上——状态机、作业票、审计、LOTO——而不是押注在某个存储引擎上。存储是可替换的，业务模型才是系统的。"

### Q2：听说你们数据坏过一次？

**回答**（用第六节复盘口径，不回避、给证据、给修复）：
"是，开发期迁移重编号时出过一次本地文件锁问题，已定位根因、已修复、已加备份防线，事件备份保留在 archive/ 里可查。我们觉得这反而是工程化的证明——我们记录、复盘、修复，而不是掩盖。"

### Q3：数据丢了怎么办？

**回答**：
"三保险：每日 2:00 自动备份（保留 7 天）→ 手动备份脚本 → 恢复脚本一键还原。生产环境切 PostgreSQL 后，还能叠加数据库自身的备份策略。"

### Q4：为什么不直接用 PostgreSQL 参赛？

**回答**：
"两个原因：① 比赛演示环境不可控，评委机器可能没装 PostgreSQL，我们要保证**拷过去就能跑**；② PGlite 是真实 PostgreSQL 引擎，SQL 与生产完全兼容，切到独立 PostgreSQL 不需要改任何业务代码——我们把它当'演示专用形态'，不是技术降级。"

### Q5：数据量大了怎么办？（进阶追问）

**回答**：
"PGlite 定位明确，不做大数据量承诺。路径是：数据量上来 → DB_TYPE=postgres 切换独立实例 → 连接池（max 可配）→ 后续可加读写分离。迁移工具已备好，表结构完全一致。"

## 八、话术纪律（别踩的坑）

1. **别吹**"PGlite 生产级"——承认它是演示选型，反而加分。
2. **别瞒** 9/12 事件——评委查 data/ 目录就能看到 corrupt 备份，主动讲比被翻出来强一百倍。
3. **别说**"嵌入式数据库没问题"——边界要主动讲：单进程、无流复制、无故障转移。
4. **别漏**迁移脚本只覆盖 12 张表的缺口——答辩前补全或准备好解释。
5. **必带演示**：现场演示一次 backup.sh + restore.sh，比说十句都有说服力。
